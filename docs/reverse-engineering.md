# Compatibility notes

These notes record observed interfaces and public workflow behavior used to design the independent `lrtl` implementation. They do not reproduce LRTimelapse code.

## Local installation observations

- The installed version is LRTimelapse 7.5.5 under `C:\Program Files\LRTimelapse 7`.
- `LRTimelapse.cmd` starts the bundled Java runtime with `-jar LRTimelapse.jar`; the JAR manifest names `lrtimelapse.LRTimelapseApp` as its entry point. The GUI EXE is a 32-bit PE launcher analyzed with Ghidra, rather than the main metadata-processing implementation.
- The installation includes separate `exiftool.exe`, `ffmpeg.exe`, and `dnglab.exe` programs. These indicate separate metadata, video, and RAW-processing components for future interoperability work.
- The installed locale resources expose actions for keyframe toggling, XMP metadata initialization/reload/save, and transitions. Their helper labels identify four stars as a default keyframe and five stars as a crop keyframe.
- A limited scan of app-class string constants found Adobe's Camera Raw XMP namespace URI and workflow names for keyframes, Auto-Transition, Holy Grail, and visual deflicker. No product code or class output is part of this repository.
- `javap` inspection of the installed 7.5.5 JAR's visual-deflicker call path showed per-sequence fields for pass count, smoothing factor, constant-target mode, accuracy, and workflow state. The worker receives the selected sequence, accuracy, pass count, workflow value, `smoothingFactor * 80`, and constant-target flag. Each pass visits ordered frame records, reads a per-frame numeric measurement, derives a smoothed target curve through `lrtimelapse.eA` and a regularized solver (`Pia`), then stores per-frame correction deltas. This establishes the control flow and parameter roles; the exact luminance statistic, ROI sampling, curve constraints, and pixel-development math are not fully identified from this bytecode trace.
- `javap -p` on the installed JAR's `lrtimelapse.settings.SequenceProperties` exposes sequence settings named `holyGrailReduceDeflicker`, `holyGrailRotate`, `holyGrailStretch`, and `workflowHolyGrailWizard`. This confirms separate sequence state and curve adjustment controls. The wizard's full EXIF calculation, upstream fitting, and correction-layer serialization were not reconstructed, so the current implementation uses a documented exposure-equivalent model and does not claim numerical parity.
- Further `javap` inspection mapped the Holy Grail UI controls into the sequence fields: the Rotate control ranges from -4.00 to +4.00, the Stretch control from -1.50 to +1.50, and a third value is stored as `holyGrailReduceDeflicker`. The installed sequence model persists these values outside per-image XMP. Upstream curve fitting and correction-layer serialization remain unknown.
- A follow-up bytecode trace mapped the two sliders to `holyGrailRotate` and `holyGrailStretch`: the Rotate slider stores integer hundredths in `[-400, 400]`, and the Stretch slider stores hundredths in `[-150, 150]`. The Holy Grail curve helper first normalizes its input values to `[-0.5, +0.5]`, then applies `normalized * stretch + (frameIndex / frameCount - 0.5) * rotate + offset`. The UI passes a zero offset. This describes the helper's curve shaping stage only; it does not identify the upstream brightness model or the final XMP-writing layer.
- The Holy Grail Wizard worker performs a grid search over Stretch in increments of 0.02 and Rotate in increments of 0.04. Its Stretch objective is the sum of `abs(curve[i] - smoothCurve[i])`; its Rotate objective is the sum of `abs(smoothCurve[i])`. The worker reads the raw and smoothed arrays through `tQa.A()` and `tQa.m()` after `cOM7.a(...)` stores them. This identifies the L1 objectives, although the upstream curve construction and exact regularized smoother are still not fully mapped. The `holyGrailReduceDeflicker` slider value is passed into the curve interpolation/regularization helper.
- A follow-up scan of class-file string constants found local-correction names such as `crs:LocalExposure2012`, `crs:LocalContrast2012`, and `crs:LocalColorGradeShadowSat`, alongside mask fields such as `crs:CorrectionMasks` and `crs:CorrectionAmount`. This confirms the installed program recognizes a richer local-adjustment XMP vocabulary; constants alone do not establish its serialization or interpolation behavior. The OSS CLI therefore preserves these fields without editing them.
- The installed JAR contains three XMP templates (`empty.xmp`, `raw_m_1.xmp`, and `raw_m_2.xmp`). The empty template uses scalar child elements for Camera Raw version/settings and crop defaults (`CropTop/Left=0`, `CropBottom/Right=1`, `CropAngle=0`), plus a structured `crs:Look` with `Name` and `Amount` attributes. The RAW templates contain many more scalar slider fields, along with booleans, enum-like values, and structured properties. These templates establish packet shape and vocabulary, but not which fields Auto-Transition interpolates.
- Bytecode metadata names sequence-level fields `rating`, `workflowKeyframes`, and `workflowAutoTransition`, and a global `initializationCreatesKeyframes` setting. This distinguishes per-sequence workflow state from per-image XMP ratings. The observed names do not reveal the full runtime keyframe algorithm.

## Public workflow behavior

- The official workflow describes XMP files as the exchange layer between LRTimelapse and Lightroom. Users choose keyframes, edit those images, save metadata, then run Auto-Transition to calculate settings for intervening frames.
- The official Visual Workflow enables the Holy Grail wizard for manual-mode sequences where exposure time and/or ISO changed during capture, and describes its orange curve as compensation for those camera adjustments. LRTimelapse offers rotate/stretch controls for shaping that curve.
- The current official Visual Workflow also gates the wizard on a manual-mode sequence. lrtl only creates automatic 2*/3* markers when EXIF explicitly reports Manual on every frame; `--mark-jumps` is an override for sequences whose camera omitted mode metadata.
- LRTimelapse's developer describes 2-star/3-star ratings as internal Holy Grail keyframes that mark camera-setting jumps and must not be overwritten by ordinary 4-star keyframes. This supports the separate marker model; it does not establish the exact correction values stored by the wizard.
- The official Keyframes Wizard describes its suggestions as an automatic analysis of the sequence luminance progression. A CFR decompile of the installed 7.5.5 action dispatcher shows its `AUTOKF` branch only records a “User action: Keyframe Wizard” event; it contains no candidate-selection logic. The adjacent `EVENKF` action calls a method that enables and selects a helper panel. This narrows the menu-dispatch path but does not identify the wizard's actual worker or its selection algorithm. The installed JAR scan also exposed the global `initializationCreatesKeyframes` setting. `lrtl keyframes` therefore uses its own explicit luminance-curve heuristic and should not be treated as a behavioral clone.
- The installed Japanese and English resources expose a separate “create keyframes (evenly spaced)” action. `lrtl keyframes --evenly-spaced` offers a comparable endpoint-anchored uniform placement and skips pixel decoding, so it also works on RAW image sequences. It does not reproduce LRT's exact count adjustment around existing keyframes.
- Keyframes appear as four-star ratings in Lightroom. The current official guide also documents manually adding and removing keyframes with the `1` and `0` keys.
- LRTimelapse 7.4 release notes state that first/last images are not automatically keyframes, a single keyframe is used as a reference for other frames, and a sequence without keyframes uses the first image as its reference.
- LRTimelapse 7.4 also describes linear transitions at sequence ends. The implementation uses existing numeric settings on the first/last image as virtual edge anchors when present, while leaving those endpoint files unchanged. If an edge value is absent, it falls back to the nearest keyframe's value for that property.

## Implemented compatibility choices

- Four-star ratings (`xmp:Rating=4`) identify ordinary keyframes; five-star ratings (`xmp:Rating=5`) identify crop keyframes according to the installed labels.
- A marker made by `lrtl mark` records the prior Lightroom rating in its own namespace so `lrtl unmark` can restore it. It always keeps the Adobe rating marker that Lightroom filters can see.
- Transitions operate only on an explicit list of scalar numeric Camera Raw properties. It includes selected legacy controls listed with integer/real types in Adobe's Camera Raw namespace reference and common newer Develop controls such as `Exposure2012`, `Contrast2012`, and `Highlights2012`. Boolean flags, categorical values such as `CropUnits`, circular color-wheel hue values, profiles, masks, arrays, and tone curves are left untouched because a numeric encoding alone does not make linear interpolation meaningful. Slider-style legacy hue offsets such as `RedHue` remain ordinary scalar controls.
- `holy-grail` reads standard exposure time, ISO, and (unless `--ignore-aperture` is set) FNumber tags from supported JPEG/TIFF/CR2/CR3/DNG/RW2 files. It calculates a per-frame exposure-equivalent value `log2(time × ISO / FNumber²)`, then writes its difference from the first frame as an additive `crs:Exposure2012` correction. The applied correction is recorded under the project's `ol` namespace to make reruns replace the previous result and to support `--reset`; this is an lrtl-specific bookkeeping field, not an LRTimelapse field. LRT-compatible output is a sidecar XMP. The implementation does not decode embedded EXIF from every RAW container or read developed-image luminance.
- Optional `--stretch` and `--rotate` controls reproduce the observed curve-helper geometry over the EXIF exposure-equivalent curve: min/max normalization to `[-0.5, +0.5]`, multiplication by Stretch, and addition of a centered linear trend scaled by Rotate. `--auto-shape` uses LRT's observed two-stage search ranges and L1 objectives with a tricube-weighted local linear LOWESS smoother. Direct calls into the installed `eA` helper and `Pia` smoother showed the wrapper's 1.5 setting resolves to a window of `n-1` samples; lrtl uses that effective window. Holy Grail's upstream brightness curve, its full regularized fitting path, Lightroom-value composition, and background correction layer remain unimplemented.
- By default, `holy-grail` also marks isolated EXIF setting changes as adjacent `xmp:Rating=2` / `xmp:Rating=3` keyframe pairs, with lrtl metadata to preserve and restore any prior rating. These markers follow the public LRT conventions, while the numeric correction is still written to `crs:Exposure2012`; this differs from LRT's background correction layer and can overlap with Lightroom's user Exposure edits.
- Every write is atomic and makes a timestamped sidecar backup unless `--no-backup` is provided. Interpolation is preview-only unless `--write` is provided.
- This milestone reads external sidecars only. It does not inspect or update XMP embedded in JPEG, TIFF, or DNG files, nor compare embedded and sidecar timestamps.
- `render --apply-xmp-crop` reads `crs:HasCrop` and the crop bounds from sidecars, applies axis-aligned crops, then scales each crop to the input frame dimensions. Nonzero `crs:CropAngle` is rejected because rotated crop geometry has not been validated against Camera Raw. The bundled XMP template uses normalized 0-to-1 crop bounds; when `HasCrop` is absent, non-default bounds are treated as an active crop.
- Local correction masks and their per-mask settings remain out of scope until representative XMP packets and transition behavior can be compared safely.
