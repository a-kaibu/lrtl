# Compatibility notes

These notes record observed interfaces and public workflow behavior used to design the independent `lrtl` implementation. They do not reproduce LRTimelapse code.

## Local installation observations

- The installed version is LRTimelapse 7.5.5 under `C:\Program Files\LRTimelapse 7`.
- `LRTimelapse.cmd` starts the bundled Java runtime with `-jar LRTimelapse.jar`; the JAR manifest names `lrtimelapse.LRTimelapseApp` as its entry point. The GUI EXE is a 32-bit PE launcher analyzed with Ghidra, rather than the main metadata-processing implementation.
- The installation includes separate `exiftool.exe`, `ffmpeg.exe`, and `dnglab.exe` programs. The installed DNGLab reports version 0.7.2; `dnglab analyze --srgb <RAW>` writes a 16-bit sRGB TIFF to stdout. `lrtl render --raw-develop` can call a user-selected DNGLab executable through this public CLI and consume that TIFF. It does not depend on or redistribute the copy bundled with LRTimelapse. The upstream DNGLab project identifies itself as alpha software and says its Windows binary is untested, so camera support and output stability remain external limitations.
- The installed DNGLab 0.7.2 also exposes `dnglab convert <INPUT> <OUTPUT>`, with lossless or uncompressed compression, optional preview/thumbnail and embedded-RAW controls, and a crop choice. The independent `import --convert-dng` path invokes one conversion process per supported RAW image, requests lossless or uncompressed output, keeps the source modification time when available, and copies any adjacent XMP sidecar alongside the converted DNG. It does not invoke or redistribute the executable from the LRTimelapse installation; users supply their own DNGLab. DNGLab's alpha status and untested Windows build apply to this conversion path as well.
- The installed locale resources expose actions for keyframe toggling, XMP metadata initialization/reload/save, and transitions. Their helper labels identify four stars as a default keyframe and five stars as a crop keyframe.
- A limited scan of app-class string constants found Adobe's Camera Raw XMP namespace URI and workflow names for keyframes, Auto-Transition, Holy Grail, and visual deflicker. No product code or class output is part of this repository.
- `javap` inspection of the installed 7.5.5 JAR's visual-deflicker call path showed per-sequence fields for pass count, smoothing factor, constant-target mode, accuracy, and workflow state. The worker receives the selected sequence, accuracy, pass count, workflow value, `smoothingFactor * 80`, and constant-target flag. Each pass visits ordered frame records, reads a per-frame numeric measurement, derives a smoothed target curve through `lrtimelapse.eA` and a regularized solver (`Pia`), then stores per-frame correction deltas. This establishes the control flow and parameter roles; the exact luminance statistic, ROI sampling, curve constraints, and pixel-development math are not fully identified from this bytecode trace.
- A narrower trace of the `eA.A(length, indices, values, smoothing)` helper found that it constructs `Pia` with a bandwidth proportional to `smoothing * length / sampleCount`. The `Pia` path computes a tricube-weighted local linear regression over a moving nearest-sample window; the traced caller sets the robust-iteration count to zero, so this call makes a single smoothing pass. `lrtl deflicker --smoother lowess` now offers the same general regression family, with its own radius-to-window conversion. This does not identify LRT's input luminance statistic, sample selection semantics, correction response, or final developed pixels, and does not claim numerical parity.
- `javap -p` on the installed JAR's `lrtimelapse.settings.SequenceProperties` exposes sequence settings named `holyGrailReduceDeflicker`, `holyGrailRotate`, `holyGrailStretch`, and `workflowHolyGrailWizard`. This confirms separate sequence state and curve adjustment controls. The wizard's full EXIF calculation, upstream fitting, and correction-layer serialization were not reconstructed, so the current implementation uses a documented exposure-equivalent model and does not claim numerical parity.
- Further `javap` inspection mapped the Holy Grail UI controls into the sequence fields: the Rotate control ranges from -4.00 to +4.00, the Stretch control from -1.50 to +1.50, and a third value is stored as `holyGrailReduceDeflicker`. The installed sequence model persists these values outside per-image XMP. Upstream curve fitting and correction-layer serialization remain unknown.
- A follow-up bytecode trace mapped the two sliders to `holyGrailRotate` and `holyGrailStretch`: the Rotate slider stores integer hundredths in `[-400, 400]`, and the Stretch slider stores hundredths in `[-150, 150]`. The Holy Grail curve helper first normalizes its input values to `[-0.5, +0.5]`, then applies `normalized * stretch + (frameIndex / frameCount - 0.5) * rotate + offset`. The UI passes a zero offset. This describes the helper's curve shaping stage only; it does not identify the upstream brightness model or the final XMP-writing layer.
- The Holy Grail Wizard worker performs a grid search over Stretch in increments of 0.02 and Rotate in increments of 0.04. Its Stretch objective is the sum of `abs(curve[i] - smoothCurve[i])`; its Rotate objective is the sum of `abs(smoothCurve[i])`. The worker reads the raw and smoothed arrays through `tQa.A()` and `tQa.m()` after `cOM7.a(...)` stores them. This identifies the L1 objectives, although the upstream curve construction and exact regularized smoother are still not fully mapped. The `holyGrailReduceDeflicker` slider value is passed into the curve interpolation/regularization helper.
- A follow-up scan of class-file string constants found local-correction names such as `crs:LocalExposure2012`, `crs:LocalContrast2012`, and `crs:LocalColorGradeShadowSat`, alongside mask fields such as `crs:CorrectionMasks` and `crs:CorrectionAmount`. This confirms the installed program recognizes a richer local-adjustment XMP vocabulary; constants alone do not establish its serialization or interpolation behavior.
- The installed JAR contains three XMP templates (`empty.xmp`, `raw_m_1.xmp`, and `raw_m_2.xmp`). The empty template uses scalar child elements for Camera Raw version/settings and crop defaults (`CropTop/Left=0`, `CropBottom/Right=1`, `CropAngle=0`), plus a structured `crs:Look` with `Name` and `Amount` attributes. The RAW templates contain many more scalar slider fields, along with booleans, enum-like values, and structured properties. `raw_m_1.xmp` stores the legacy master `ToneCurve` as an `rdf:Seq` of `rdf:li` coordinate pairs (`0, 0`, `255, 255`); `raw_m_2.xmp` stores `ToneCurvePV2012` in the same shape. These templates establish packet shape and vocabulary, but not which fields Auto-Transition interpolates.
- Bytecode metadata names sequence-level fields `rating`, `workflowKeyframes`, and `workflowAutoTransition`, and a global `initializationCreatesKeyframes` setting. This distinguishes per-sequence workflow state from per-image XMP ratings. The observed names do not reveal the full runtime keyframe algorithm.

## Public workflow behavior

- The official workflow describes XMP files as the exchange layer between LRTimelapse and Lightroom. Users choose keyframes, edit those images, save metadata, then run Auto-Transition to calculate settings for intervening frames.
- The official Long-Term / Construction workflow describes filtering sequences by Luminance, Contrast, and Hue, then applying Deflicker and Motion Blur to the more consistent subset. The workflow page describes paired low/high filter limits but does not publish the underlying metric equations.
- The official Visual Workflow enables the Holy Grail wizard for manual-mode sequences where exposure time and/or ISO changed during capture, and describes its orange curve as compensation for those camera adjustments. LRTimelapse offers rotate/stretch controls for shaping that curve.
- The current official Visual Workflow also gates the wizard on a manual-mode sequence. lrtl only creates automatic 2*/3* markers when EXIF explicitly reports Manual on every frame; `--mark-jumps` is an override for sequences whose camera omitted mode metadata.
- LRTimelapse's developer describes 2-star/3-star ratings as internal Holy Grail keyframes that mark camera-setting jumps and must not be overwritten by ordinary 4-star keyframes. This supports the separate marker model; it does not establish the exact correction values stored by the wizard.
- The official Keyframes Wizard describes its suggestions as an automatic analysis of the sequence luminance progression. A CFR decompile of the installed 7.5.5 action dispatcher shows its `AUTOKF` branch only records a “User action: Keyframe Wizard” event; it contains no candidate-selection logic. The adjacent `EVENKF` action calls a method that enables and selects a helper panel. This narrows the menu-dispatch path but does not identify the wizard's actual worker or its selection algorithm. The installed JAR scan also exposed the global `initializationCreatesKeyframes` setting. `lrtl keyframes` therefore uses its own explicit luminance-curve heuristic and should not be treated as a behavioral clone.
- The installed Japanese and English resources expose a separate “create keyframes (evenly spaced)” action. `lrtl keyframes --evenly-spaced` offers a comparable endpoint-anchored uniform placement and skips pixel decoding, so it also works on RAW image sequences. It does not reproduce LRT's exact count adjustment around existing keyframes.
- Keyframes appear as four-star ratings in Lightroom. The current official guide also documents manually adding and removing keyframes with the `1` and `0` keys.
- LRTimelapse 7.4 release notes state that first/last images are not automatically keyframes, a single keyframe is used as a reference for other frames, and a sequence without keyframes uses the first image as its reference.
- LRTimelapse 7.4 also describes linear transitions at sequence ends. The implementation uses existing numeric settings on the first/last image as virtual edge anchors when present, while leaving those endpoint files unchanged. If an edge value is absent, it falls back to the nearest keyframe's value for that property.

## Implemented compatibility choices

- Four-star ratings (`xmp:Rating=4`) identify ordinary keyframes; five-star ratings (`xmp:Rating=5`) identify crop keyframes according to the installed labels.
- A marker made by `lrtl mark` records the prior Lightroom rating in its own namespace so `lrtl unmark` can restore it. It always keeps the Adobe rating marker that Lightroom filters can see.
- Transitions operate on an explicit allowlist of 131 scalar numeric Camera Raw properties. The list combines legacy controls in [Adobe's Camera Raw namespace reference](https://github.com/adobe/xmp-docs/blob/master/XMPNamespaces/crs.md), global scalar controls present in the installed LRTimelapse 7.5.5 `raw_m_1.xmp` and `raw_m_2.xmp` templates, and continuous scalar fields in its runtime property registry. It includes legacy Clarity, Fill Light, Highlight Recovery, incremental white-balance values, HDR maximum value, color-wheel angles, and Defringe hue bounds absent from the templates. HSL `HueAdjustment*` values are signed band-shift amounts and use linear interpolation; selected color-grade/split-toning angles and Defringe hue bounds use shortest-arc interpolation on a 360-degree circle. For structured point-curve fields, lrtl copies the first frame's global `ToneCurve`, `ToneCurveName`, `ToneCurveName2012`, `ToneCurvePV2012`, and RGB channel variants to every later frame instead of animating them. LRT 7.1 notes explicitly say point curves cannot be animated and are populated from the first image. Adobe's public namespace describes `ToneCurve` as an ordered array of points. LRT also documents equalizing Look, Preset, Tone Curve, and PointColors. lrtl copies matching top-level `Look`, `Preset`, and `PointColors` values from the first frame as a compatibility choice; the release notes do not state which frame supplies those three values, so this exact source rule remains unverified. For `GradientBasedCorrections`, `CircularGradientBasedCorrections`, `DepthBasedCorrections`, `MaskGroupBasedCorrections`, and `PaintBasedCorrections`, lrtl interpolates `CorrectionAmount` and numeric `Local*` properties only when the correction has a common `CorrectionSyncID` in the target frame. It also interpolates a whitelist of numeric shape fields (for example `FullX`, `ZeroX`, `Angle`, and `Radius`) when the nested mask has a common `MaskSyncID`; hue-like local properties and mask angles use shortest-arc interpolation. This follows LRT's developer guidance that initialized masks can be moved/resized at keyframes and Auto-Transition animates them. Selector/range data, brush `Dabs`, local tone curves, selectors copied from the first mask, unmatched sync IDs, and XMP mask pixel rendering remain unsupported. This is a compatibility approximation; numerical parity has not been checked against LRT 7.5.5.
- `holy-grail` reads standard exposure time, ISO, and (unless `--ignore-aperture` is set) FNumber tags from supported JPEG/TIFF/CR2/CR3/DNG/RW2 files. It calculates a per-frame exposure-equivalent value `log2(time × ISO / FNumber²)`, then writes its difference from the first frame as an additive `crs:Exposure2012` correction. The applied correction is recorded under the project's `ol` namespace to make reruns replace the previous result and to support `--reset`; this is an lrtl-specific bookkeeping field, not an LRTimelapse field. LRT-compatible output is a sidecar XMP. The implementation does not decode embedded EXIF from every RAW container or read developed-image luminance.
- `deflicker --write` measures linear-light sRGB median luminance in a selected image rectangle, smooths log2 luminance with the local Gaussian smoother (or targets its sequence median), and adds the resulting per-frame stop deltas to `crs:Exposure2012`. It tracks only its own additive delta in `ol:DeflickerCorrection2012` so recalculation replaces that contribution and `--reset` preserves Holy Grail and user exposure values. With `--raw-preview` or `--raw-develop`, it can also analyze the selected RAW preview/developed pixels. This is an independent approximation, not the installed program's Visual Deflicker worker described above.
- `deflicker --smoother lowess` uses the local linear tricube regression in `lowess.go`, selecting up to `2*radius+1` neighboring frames per estimate. It is an optional smoothing choice informed by the installed worker's observed kernel, while Gaussian remains the default and the surrounding luminance measurement and multi-pass correction remain independent approximations.
- `preview` writes a static SVG plot of per-frame log2 linear-sRGB median luminance relative to the first image, sidecar `crs:Exposure2012` relative to the first value, and 2*/3*/4*/5* keyframe markers. It can use selected embedded RAW previews or DNGLab-developed TIFFs as image inputs. This is a numeric sequence chart, not the installed app's rendered visual preview.
- `long-term` samples up to a 64×64 grid and records median linear-sRGB luminance, the 90th-to-10th percentile spread of log2 luminance in stops, and saturation-weighted circular mean hue. Optional inclusive ranges create a versioned JSON selection manifest; `render --selection` validates its source directory, exact frame set, file sizes, and modification times before rendering only included images. This reproduces the broad filter-then-render workflow, not LRT's undisclosed metric formulas or GUI.
- `import` copies supported still images from a folder, optionally recurses into subfolders, copies matching XMP sidecars, skips JPEGs, sorts by XMP/EXIF capture time, or renames by capture time. `--convert-dng` invokes a user-supplied DNGLab for supported RAW files while copying other images and matching XMP. It supports the DNGLab lossless/uncompressed choices but not lossy compression or resizing. `import-video` invokes user-supplied FFmpeg to extract all decoded video frames, or samples at a requested fps, to an ordered JPG/PNG sequence. Both import paths check output collisions; DNG conversion stages each output before publishing it. LRT sequence-state transfer, video preview/splitting, and DNG resizing remain unimplemented.
- `timeshift` shifts scalar XMP `exif:DateTimeOriginal`, `exif:DateTimeDigitized`, and `xmp:CreateDate` values by a fixed duration. If no capture date is present in the sidecar, it reads the image's EXIF capture time and writes the shifted `exif:DateTimeOriginal` to a sidecar. It leaves `xmp:ModifyDate` and embedded image metadata unchanged. The operation previews by default and writes with sidecar backups only after `--write`; it is an XMP-sidecar operation, not a claim of exact parity with LRT's metadata UI.
- The installed `RenderPreset` stores Motion Blur as an enable flag plus an integer level. Bytecode inspection of the render dialog shows its seven choices store 2, 3, 4, 5, 10, 15, or 20, and its getter returns those same values. Static inspection of `mQa`'s render command builder and `A(int,float)` shows LRT emits `tmix=frames=N:weights='...'`; it generates each weight as `(i/N)^1.5` for `i=1..N`, formats it to three decimal places, and joins values with spaces. Weights run from the oldest frame to the current frame, so the current frame receives weight 1. FFmpeg's `tmix` fills its first window by cloning the first frame and normalizes weights by their sum when no explicit scale is set. `render --motion-blur N` follows that frame schedule and weight curve in Pure Go. Pixel values remain an approximation because lrtl blends 8-bit RGB while the inspected LRT render filter runs on a 10-bit YUV444 path; no rendered pixel-by-pixel comparison has been made. See the [FFmpeg filter documentation](https://ffmpeg.org/ffmpeg-filters.html#tmix) and [`vf_mix.c`](https://www.ffmpeg.org/doxygen/8.1/vf__mix_8c_source.html) for `tmix` behavior.
- `--raw-preview` walks classic TIFF IFD, ExifIFD, and SubIFD links, tests JPEG/PNG/TIFF interchange/strip segments, and selects the largest decodable embedded image for CR2/DNG/NEF/NRW/ARW/PEF/SRW extensions. Olympus ORF uses TIFF-layout directories with its recognized custom magic; previews in MakerNotes-only locations are not extracted. Panasonic RW2 uses the TIFF directory layout with magic 85 and its IFD0 tag 0x002e embedded JPEG. Fujifilm RAF uses the big-endian JPEG offset and length fields from its header. For CR3, the parser looks for the Canon UUID preview record, bounds-checks its declared JPEG length, and validates the embedded JPEG. `render`, `keyframes`, `preview`, and `deflicker` can use those images when explicitly requested. This is the camera's embedded preview, not demosaicing, white-balance handling, or Camera Raw development; CR3 files without that UUID preview are not handled by this path. The CR3 layout was cross-checked against [ExifTool's public QuickTime parser notes](https://github.com/exiftool/exiftool/blob/master/lib/Image/ExifTool/QuickTime.pm#L761), RW2 against [libopenraw's RW2 notes](https://libopenraw.freedesktop.org/formats/rw2/) and [ExifTool's Panasonic tag definitions](https://github.com/exiftool/exiftool/blob/master/lib/Image/ExifTool/PanasonicRaw.pm#L193), and ORF/RAF against their [libopenraw format notes](https://libopenraw.freedesktop.org/formats/orf/) and [RAF header notes](https://libopenraw.freedesktop.org/formats/raf/); lrtl has independent Go parsing code.
- `--raw-develop` invokes an independently installed DNGLab with `analyze --loglevel error --srgb <RAW>`, reads its 16-bit sRGB TIFF from stdout, and supplies that image to `render`, luminance-based `keyframes`, `preview`, and `deflicker`. Analysis commands can separately apply sidecar `crs:Exposure2012` and rotated crop geometry before measuring luminance; `render` has equivalent options. `--dnglab` selects the executable; otherwise `dnglab` must be available on `PATH`. The accepted sequence extensions follow the public DNGLab supported-format table. This integrates an external CLI rather than copying its code or bundling the LRTimelapse installation. It does not read Camera Raw XMP into DNGLab, and DNGLab's demosaic, white balance, tone, and color output are not expected to match Adobe Camera Raw. The upstream project describes DNGLab as alpha software and its Windows binary as untested. RAW developed output is capped at 1 GiB per frame in memory; video rendering then converts to its 8-bit path.
- Optional `--stretch` and `--rotate` controls reproduce the observed curve-helper geometry over the EXIF exposure-equivalent curve: min/max normalization to `[-0.5, +0.5]`, multiplication by Stretch, and addition of a centered linear trend scaled by Rotate. `--auto-shape` uses LRT's observed two-stage search ranges and L1 objectives with a tricube-weighted local linear LOWESS smoother. Direct calls into the installed `eA` helper and `Pia` smoother showed the wrapper's 1.5 setting resolves to a window of `n-1` samples; lrtl uses that effective window. Holy Grail's upstream brightness curve, its full regularized fitting path, Lightroom-value composition, and background correction layer remain unimplemented.
- By default, `holy-grail` also marks isolated EXIF setting changes as adjacent `xmp:Rating=2` / `xmp:Rating=3` keyframe pairs, with lrtl metadata to preserve and restore any prior rating. These markers follow the public LRT conventions, while the numeric correction is still written to `crs:Exposure2012`; this differs from LRT's background correction layer and can overlap with Lightroom's user Exposure edits.
- Every write is atomic and makes a timestamped sidecar backup unless `--no-backup` is provided. Interpolation is preview-only unless `--write` is provided.
- This milestone reads external sidecars only. It does not inspect or update XMP embedded in JPEG, TIFF, or DNG files, nor compare embedded and sidecar timestamps.
- `render --apply-xmp-crop` reads `crs:HasCrop`, normalized crop bounds, and `crs:CropAngle` from sidecars. For nonzero angles, it follows Lightroom's published coordinate convention: positive angles rotate the crop clockwise, the diagonal crop corners are rotated back to derive the level crop bounds, and an inverse affine map samples the source into the fixed output frame. Catmull-Rom resampling is used for both angled and axis-aligned crops. The bundled XMP template uses 0-to-1 crop bounds; when `HasCrop` is absent, non-default bounds or angle are treated as an active crop. The geometry implementation follows the public [Camera Raw XMP namespace](https://github.com/adobe/xmp-docs/blob/master/XMPNamespaces/crs.md) and Adobe Community's [crop-corner coordinate walkthrough](https://community.adobe.com/questions-675/sdk-computing-the-corners-of-a-crop-rectangle-962108); numerical parity has not yet been checked against a Camera Raw render.
- `render --apply-xmp-basic` also reads the scalar Exposure/Contrast/Highlights/Shadows/Whites/Blacks/Vibrance/Saturation controls and explicit master/RGB point curves from XMP. Curves are accepted as comma/semicolon-separated scalar pairs or ordered RDF arrays; the renderer builds 8-bit lookup tables using PCHIP interpolation between points. Adobe documents Camera Raw `ToneCurve` as an ordered array of integer points, but the sRGB-domain LUT and tone-control equations here are independent approximations, not Adobe's RAW/render pipeline. Curve-name presets without explicit point arrays, white balance, parametric curves, local corrections, and Camera Raw profile behavior remain unsupported.
- `render --auto-orient` reads the EXIF orientation from the encoded raster, selected embedded preview, or DNGLab-developed TIFF using the existing Go metadata dependency. It applies the EXIF rotate/mirror transform before crop, tone adjustment, deflicker analysis, resize, and encoding; frames must agree in post-orientation dimensions. This is an independent pixel transform and does not update source metadata.
- Local correction mask image processing remains out of scope. The current XMP transition support only edits numeric correction and geometry fields on matching Sync IDs; it does not develop those settings onto pixels or rebuild image-dependent selectors.
